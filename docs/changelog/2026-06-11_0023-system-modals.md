# 0023 changes

Wires the two non-form system modals from the original
`0015_task_refactor_ui` design: the **Notifications Modal** and the
**Info Modal**. The shell's global `n` and `?` keys now open real
dialogs instead of pushing no-op stubs.

The Notifications Modal is a new `bubbles/table`-backed
`modal.Content` implementation under
`internal/tui/components/notifications/`. It pulls
`notifications.Log.Entries()` (newest-first ring buffer from task 0019)
at open time, renders each entry with the shared
`styles.SeverityStyle` palette, and shows `"No notifications yet"` when
the log is empty. The Info Modal reuses the existing
`internal/tui/components/help/help.go` viewport modal from task 0020,
wired through a small per-screen topic registry that today resolves to
`docs/manual/overview.md`.

Two shell stubs were retired (`notifications_stub.go`, `info_stub.go`)
and replaced with thin Screen adapters that host a `*modal.Modal` and
pop themselves on `modal.ResolvedMsg`. The `notifier` consumer
interface in the shell grew an `Entries()` method so the notifications
modal can read from `m.log` without dragging the concrete
`*notifications.Log` into the shell's compile-time API.

## Decisions

- **Modal hosting via Screen adapter, not native overlay.** The shell
  currently has only a Screen stack (task 0021). Each new screen
  (`notificationsScreen`, `infoScreen`) owns a `*modal.Modal` and
  renders `modal.View()` from its `Body`. — **Why:** task 0023's scope
  is "wire the global keys to real dialogs," not "redesign the shell."
  Adding a native overlay layer would change the shell's contract; this
  approach is strictly additive and preserves every existing test. A
  future overlay refactor can land via a dedicated ADR.
- **Separate `LogReader` interface in the modal package.** The
  notifications modal depends on a one-method `LogReader { Entries()
  []notifications.Notification }` rather than the concrete `*Log`. —
  **Why:** ISP / DIP — the modal only needs the read side; tests inject
  a `fakeLog` instead of constructing a ring buffer; the modal does not
  reach into the producer side of the log.
- **Snapshot on open, not live refresh.** `New` calls `Entries()` once;
  reopening pulls fresh data. — **Why:** spelled out in
  `tasks/.../description.md`; a live feed would force the modal to
  subscribe to `NotificationMsg`, doubling the toast/log fan-out and
  introducing ordering bugs.
- **`notifier` interface extended in the shell.** Added `Entries()` to
  the consumer-side interface. — **Why:** the shell now mounts a screen
  whose modal needs read access; the alternative (casting `m.log` to
  `*notifications.Log` at the call site) breaks the
  interface-substitution test that the shell relies on for fakes.
- **Topic registry returns a constant for now.** `topicFor(_ Screen)
  string` always returns `ManualOverview`. — **Why:** the description
  says per-screen overrides are out of scope ("add as needed when
  screens land"). Keeping the dispatch site future-proof avoids a
  second migration when concrete screens arrive in tasks 0024+.
- **`modalSize` floors to a usable rectangle.** The shell mounts the
  modal at push time using its current `width`/`height`; both can be
  zero before the first `WindowSizeMsg`. The floor (40×10) guarantees
  the modal opens with usable dimensions even on the very first
  keystroke. — **Why:** opening a zero-sized modal would feed
  bubbles/table a non-positive dimension and either crash or render
  garbage.

### Considered but rejected

- **Replacing the Screen stack with a native modal-overlay layer.**
  Would match `docs/guidelines/charm.md` ("modals stack via
  `lipgloss.Compositor`") more literally, but is out of scope for 0023
  — and adding it now would force every existing screen test to mock a
  new overlay slot.
- **Subscribing the notifications modal to `NotificationMsg` for live
  updates.** Rejected per the description's "no live refresh" wording.
- **Driving the bubbles/table snapshot test character-by-character.**
  Bubbles/table v2 ships no exposed key for re-rendering on demand;
  `View()` is deterministic and substring assertions cover the
  observable behaviour without binding the test to ANSI escape codes.

## Assumptions

- The modal opens against the shell's current viewport, not an
  artificial fixed size — that matches the help modal's existing
  behaviour. — **Why:** users open these from arbitrary terminal sizes;
  hard-coding 80×24 would waste space on a wide window and crash a
  narrow one.
- The user's default keybindings (esc to close) are intuitive enough to
  document only in the overview manual; per-modal help text is a follow
  -on. — **Why:** task description does not call out a help footer
  inside the Notifications modal, and the existing Help modal already
  embeds its own footer.

## Other Notes

- New file: `docs/manual/overview.md` — short intro + global key list.
  Linked from the Info modal as today's default topic.
- New file: `internal/tui/shell/topics.go` — single-function topic
  registry; expected to grow per-screen entries as concrete screens
  arrive.
- The shell's `notifier` interface now mirrors the small subset of
  `*notifications.Log` the shell uses. Tests that construct a real
  `Log` continue to pass because `*Log` already satisfies the wider
  shape.
- The `stubs_test.go` file now covers the settings stub plus the two
  new screens; the older test list iterating three stubs was retired.

`Entries()` once on construction; empty log falls through to an
`EmptyMessage` view.

// new (excerpt) — column widths leave room for the modal's border and
// the per-column padding bubbles/table adds via its Cell style.
func innerSize(width, height int) (int, int) {
    w := width - modalHFrame
    if w < minContentW+levelColW+timeColW+3*cellPadding {
        w = minContentW + levelColW + timeColW + 3*cellPadding
    }
    h := height - modalVFrame
    if h < 1 {
        h = 1
    }
    return w, h
}

## Shell — modal screen adapters

```go
// new — notificationsScreen.Update forwards messages to the modal and
// pops itself once a ResolvedMsg arrives from modal.Update's batched
// command. infoScreen follows the same shape (help.New instead of
// notmodal.New).
func (s *notificationsScreen) Update(msg tea.Msg) (Screen, tea.Cmd) {
    if _, ok := msg.(modal.ResolvedMsg); ok {
        return s, popCmd()
    }
    var cmd tea.Cmd
    s.modal, cmd = s.modal.Update(msg)
    return s, cmd
}
```
